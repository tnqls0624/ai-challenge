## 1. 페르소나

### 1-1. 보호 대상자 — 김영희 (68세, 독거)

> **한 문장**: 위험을 느껴도 물어볼 사람이 곁에 없어, 혼자 판단하고 혼자 후회하는 사람.

| 항목 | 내용 |
|---|---|
| **나이·거주** | 68세, **1인 가구**. 배우자 사별 후 7년째 혼자 거주 |
| **가족** | 자녀 1명, 타지역 거주. 명절과 생일에 통화하는 정도 |
| **직업** | 은퇴. 기초연금 + 소액 예금 이자로 생활 |
| **자산 특성** | 노후 자금이 **소수 계좌에 집중**. 한 번의 피해가 전 재산 손실 |
| **디지털 숙련도** | 카카오톡·문자·은행 앱 사용 가능. **앱 설치와 본인인증은 어려움** |
| **돌봄 연결** | 노인맞춤돌봄서비스 대상. 주 1회 생활지원사 방문, 주 1~2회 안부 전화 |

**행동 특성**

- 공공기관·금융기관이라는 말에 **기본적으로 신뢰**를 부여함
- 문자는 **알림창에서 바로 확인**. 앱을 따로 열지 않음
- 모르는 번호도 **일단 받음** — 혼자 살아서 전화가 반가움
- 자녀에게 연락할 때 **"바쁜데 괜히 걱정시키는 것"** 을 우려함
- 새 앱 설치는 **누군가 대신 해주지 않으면** 하지 않음

**위험 순간의 실제 행동**

```
문자 수신 → 알림창에서 읽음 → 불안해짐 → 물어볼 사람을 떠올림
                                              ↓
                              자녀 = 바쁠 것 같아 주저
                              이웃 = 이런 걸 물어보기 민망
                                              ↓
                                    혼자 판단 → 링크를 누름
```

| 취약 지점 | 설명 |
|---|---|
| **권위 신뢰** | "검찰청입니다"에 의심을 갖지 않음 |
| **압박 하 판단 정지** | 통화 중에는 생각할 시간을 확보하지 못함 |
| **검증 경로 부재** | 공식 대표번호를 찾는 방법을 모름. 문자 속 번호를 그대로 사용 |
| **⭐ 즉시 확인할 사람의 부재** | **가족이 곁에 없음. 물어볼 대상 자체가 없는 것이 최대 취약점** |
| **고립 유도에 이미 노출** | "가족에게 말하지 말라"는 지시가 필요 없음. 이미 혼자임 |

> **독거 상태가 만드는 차이**
> 가족과 함께 사는 고령자는 배우자·자녀가 "그거 이상한데?"라고 말해줄 수 있습니다.
> 독거노인에게는 그 한마디를 해줄 사람이 없습니다. **판단 오류를 교정할 외부 장치가 전무합니다.**
> 65세 이상 1인 가구는 **23.6%(2025년, 역대 최고)** 이며 계속 증가하고 있습니다.

**주요 위험 시나리오**: 기관 사칭 → 원격제어 앱 설치 → 안전계좌 송금

**서비스에 대한 요구**

| 요구 | UI 반영 |
|---|---|
| 큰 글씨 | 본문 최소 18sp |
| 쉬운 문장 | "위험도 91점" ❌ → "매우 위험" ✅ |
| 한 번에 하나의 행동 | 한 화면에 핵심 CTA 1개 |
| 이유를 알고 싶음 | 근거 최대 3줄 |
| 누르기 쉬운 버튼 | 버튼 높이 최소 56dp |

**디자인 제약**

- 노안으로 작은 글씨 판독이 어려움 → 폰트 크기·대비 확보 필수
- 색상만으로 구분하는 UI는 인지되지 않을 수 있음 → **아이콘·텍스트 병행**
- 실수로 뒤로 가기를 누르는 경우가 있음 → **위험 안내가 즉시 사라지지 않아야 함**
- 긴 안내문은 읽지 않음 → 3줄 이내

### 1-2. 보호자 — 박지은 (42세, 생활지원사)

> **한 문장**: 25명의 어르신을 혼자 담당하면서, 누구에게 먼저 가야 하는지 매일 판단해야 하는 사람.

| 항목 | 내용 |
|---|---|
| **나이·직무** | 42세, 노인맞춤돌봄서비스 **생활지원사** |
| **담당 규모** | **20~25명**의 독거 어르신 |
| **업무 내용** | 안부확인, 일상생활지원, **ICT 안전지원**, 생활교육, 연계서비스 |
| **근무 형태** | 방문 + 전화. 이동 중이 많아 **모바일 웹** 사용 비중 높음 |
| **디지털 숙련도** | 높음. 업무용 시스템 사용에 익숙 |

> **직무 근거**: 생활지원사의 공식 업무에 **"ICT 관리교육, ICT 안전지원"** 이 이미 포함되어 있습니다.
> 돈워리는 새로운 업무를 추가하는 것이 아니라, **기존 직무를 수행할 도구**를 제공합니다.

**현재 겪는 문제**

```
[현재]  어르신이 문자 수신 → 통화 → 앱 설치 → 송금
        → ... → 주 1회 방문 때 우연히 알게 됨
                        ↑
              이미 회복 불가능한 시점

[돈워리]  어르신이 문자 수신 → 위험 판정 → 즉시 알림 → 전화 확인
                                    ↑
                          행동 전환 이전 시점
```

**행동 특성**

- 담당 인원이 많아 **개별 상황을 상시 파악할 수 없음**
- 이동 중 알림을 받으므로 **한눈에 우선순위를 판단**해야 함
- 어르신과 이미 신뢰 관계가 있어 **전화하면 받고, 말을 들음**
- 업무 기록을 남겨야 함 (돌봄 실적 관리)

**자녀 보호자와의 결정적 차이**

| | 자녀 (1:1) | 생활지원사 (1:25) |
|---|---|---|
| 담당 인원 | 1명 | **20~25명** |
| 알림 빈도 | 하루 0~1건 | **하루 여러 건 가능** |
| 필요한 것 | 알림 하나 | **우선순위 판단 화면** |
| 관계 | 가족 | 직무 |
| 개입 권한 | 감정적 설득 | **직무상 정당한 개입** |

> **설계 함의**: 이 차이가 **보호자 웹을 "알림 확인"이 아닌 "관리 대시보드"로** 만듭니다.
> 25명 중 누가 지금 가장 위험한지를 한 화면에서 판단할 수 있어야 합니다.
> 자녀 보호자에게는 없어도 되던 기능이, 생활지원사에게는 **필수**입니다.

**서비스에 대한 요구**

| 요구 | UI 반영 |
|---|---|
| 앱 설치 없이 확인 | **웹 URL 접속만으로** 사용 가능 |
| 담당 전체를 한눈에 | **위험 순 정렬된 목록**이 첫 화면 |
| 30초 안에 상황 파악 | 위험 유형·시각·행동 신호를 카드에 |
| 즉시 전화 | **[바로 전화하기]** 버튼 고정 배치 |
| 이동 중 사용 | **모바일 우선** 반응형 (자녀 페르소나와 반대) |
| 업무 기록 | 대응 이력 자동 기록 |

### 1-3. 보조 보호자 — 이수빈 (35세, 자녀)

> 독거노인이 주 타깃이지만, **가족이 있는 경우도 지원**합니다. 보호자 유형 중 하나로 다룹니다.

| 항목 | 내용 |
|---|---|
| **관계** | 김영희의 자녀. 타지역 거주 |
| **직업** | 직장인. 근무 중 **데스크톱 환경** |
| **연락 빈도** | 주 1~2회 통화 |

**요구와 우려의 균형** — 생활지원사와 다른 지점

| 요구 | 우려 |
|---|---|
| 위험 상황 즉시 확인 | 부모의 사생활을 침해하고 싶지 않음 |
| 부모에게 바로 전화 | 부모가 "감시당한다"고 느끼는 것을 원치 않음 |
| 무슨 일인지 파악 | 문자 원문 전체를 보는 것은 과하다고 생각 |

> **설계 함의**: 이 긴장 관계가 **공유 수준 3단계(최소/기본/확장)** 설계의 근거입니다.
> 생활지원사는 직무상 개입이라 이 긴장이 약하지만, 자녀는 강합니다.
> **보호자 유형에 따라 기본 공유 수준을 다르게** 설정해야 합니다.

### 1-4. 심사위원 (대회 평가자)

> **한 문장**: Android 기기 없이, 웹 URL 하나로 서비스의 실체를 판단해야 하는 사람.

| 요구 | 제품 대응 | 관련 제출물 |
|---|---|---|
| 설치 없이 서비스 확인 | 공개 웹 데모 (로그인 불필요) | 기능명세서 3번 |
| AI의 필요성 확인 | 다중 신호 분석과 근거 표시 | 기획서 5번 |
| 데이터 출처 확인 | 데이터 카드와 출처·기준일 표시 | 기획서 5번 |
| 실제 구현 여부 확인 | Android 기기와 웹 동시 데모 | 기능명세서 2번 |
| 안전성·규제 검토 | 동의·마스킹·최소수집 구조 | 기능명세서 4번 |
| 기술 검증 | 평가 대시보드와 테스트 결과 | 기능명세서 5번 |

**심사위원 여정 (웹 데모)**

```
URL 접속 → 시나리오 선택 → 가상 문자 수신 → 분석 과정 확인
   → 위험 근거 확인 → 연관 전화 발생 → 보호자 알림 확인
   → 피해 단계 선택 → 대응 체크리스트 → 평가 결과 확인
```

> **설계 제약**: 심사위원은 **설명을 듣지 못한 상태**로 접속합니다.
> 각 화면에 "지금 무엇을 보고 있는지"가 자체적으로 설명되어야 합니다.

## 2. 사용자 여정

각 여정은 **사용자 행동 / 시스템 동작 / 사용자 감정 / 이탈 위험 / 서비스 개입**의 5개 축으로 기술합니다.

---

### 2-1. 스미싱 예방 여정 (김영희)

**상황**: 오후 2시, 건강보험공단을 사칭한 미납 안내 문자 수신

| 단계 | 사용자 행동 | 시스템 동작 | 사용자 감정 | 이탈 위험 |
|---|---|---|---|---|
| 1 | 알림창에서 문자 확인 | NotificationListener가 본문 추출 | 😟 불안 | — |
| 2 | — | URL·전화번호·위험 표현 추출 | | |
| 3 | — | 기기 내 1차 규칙 분석 | | |
| 4 | — | 서버에서 URL 평판 조회 (KISA·Safe Browsing) | | |
| 5 | **위험 경고 확인** | 최종 위험 수준 생성 → 경고 화면 표시 | 😨 놀람 | ⚠️ **경고를 닫고 링크를 누를 수 있음** |
| 6 | 근거 3줄 읽음 | 판단 근거 + 지금 할 일 표시 | 🤔 이해 | ⚠️ 근거가 어려우면 무시 |
| 7 | **[확인 요청]** 누름 | 보호자에게 웹 알림 발송 | 😌 안도 | ⚠️ "귀찮게 하는 것 같아" 주저 |
| 8 | 자녀의 전화 받음 | 보호자가 상황 확인 후 전화 | 😊 안심 | — |
| 9 | 사건 안전 종료 | 사건 상태 RESOLVED 기록 | | |

**핵심 개입 지점**

| 지점 | 개입 내용 | 설계 요구 |
|---|---|---|
| **5단계** | 링크 클릭 이전에 경고 | 경고가 **알림보다 먼저** 보여야 함. 뒤로 가기로 즉시 사라지지 않아야 함 |
| **6단계** | 이해 가능한 근거 제공 | 전문용어 금지. "공식기관과 다른 주소입니다" 수준 |
| **7단계** | 보호자 연결의 심리적 장벽 해소 | "확인 요청"은 부담을 낮추는 표현. "신고"나 "도움 요청"보다 가벼움 |

> **가장 중요한 설계 판단 (7단계)**
> 김영희는 남에게 폐를 끼치는 것을 우려합니다. 버튼 문구가 **"도와주세요"** 면 누르지 않고, **"확인 요청"** 이면 누릅니다. 같은 기능이라도 문구가 전환율을 결정합니다.
>
> **독거 전환에 따른 변화**: 상대가 자녀일 때는 "바쁜데 귀찮게 하는 것"이 장벽이었습니다.
> 상대가 생활지원사일 때는 **"이런 것까지 물어봐도 되나"** 가 장벽입니다.
> 후자는 **"확인하는 것도 제 일입니다"** 라는 메시지로 해소할 수 있어, 오히려 장벽이 낮습니다.

### 2-2. 보이스피싱 예방 여정 (김영희)

**상황**: 스미싱 문자 30분 후, 주소록에 없는 번호로 전화 착신

| 단계 | 사용자 행동 | 시스템 동작 | 사용자 감정 | 이탈 위험 |
|---|---|---|---|---|
| 1 | 전화 착신 | CallScreeningService가 발신번호 확인 | 😐 평온 | — |
| 2 | — | 자체 번호 DB·신고 데이터 조회 | | |
| 3 | — | **직전 의심 문자와 시간적 연관성 확인** | | |
| 4 | **위험 전화 경고 확인** | 위험 수준 격상 → 경고 표시 | 😟 경계 | ⚠️ 경고를 무시하고 통화할 수 있음 |
| 5 | 통화함 (또는 거절) | — | 😰 압박 | ⚠️ **통화 중에는 개입 불가** |
| 6 | **통화 후 설문 응답** | 행동 신호 질문 표시 | 🤔 회상 | ⚠️ 설문을 건너뛸 수 있음 |
| 7 | "앱 설치 요구" + "송금 요구" 선택 | **CRITICAL 판정** | 😨 인지 | — |
| 8 | 보호자 알림 발송 확인 | 보호자에게 즉시 알림 | 😌 안도 | — |
| 9 | 보호 모드 안내 확인 | **30분 송금주의 보호 모드** 활성화 | | |
| 10 | 공식 대표번호로 재확인 | 공식기관 번호 안내 | 😊 안심 | — |

**핵심 개입 지점**

| 지점 | 개입 내용 | 설계 요구 |
|---|---|---|
| **3단계** | 문자–전화 연관 분석 | 단독 신호로는 CAUTION → 연관 확인 시 **HIGH 이상 격상** |
| **5단계** | **통화 중에는 개입할 수 없음** | 서비스의 구조적 한계. 통화 전·후에 집중 |
| **6단계** | 설문 응답률 확보 | 통화 종료 직후 자동 표시. 4~6개 체크박스 이내 |
| **9단계** | 송금 직전 마지막 방어선 | 30분간 위험 안내 유지 |

> **여정 2-1과 2-2의 연결이 서비스의 핵심입니다.**
> 두 여정은 **같은 사건의 1막과 2막**입니다. 문자만 보면 흔한 스미싱이고 전화만 보면 모르는 번호지만, 30분 간격으로 이어지면 명백한 기관 사칭 시나리오입니다. 이 연결을 판정에 쓰는 것이 기존 서비스와의 차별점입니다.

### 2-3. 피해 발생 여정 (김영희 + 이수빈)

**상황**: 이미 송금이 완료된 상태에서 서비스에 진입

| 단계 | 사용자 행동 | 시스템 동작 | 사용자 감정 | 설계 요구 |
|---|---|---|---|---|
| 1 | **"이미 송금함" 선택** | 피해 단계 S4 판정 | 😱 공황·수치심 | **비난하지 않는 문구** |
| 2 | — | 긴급 대응 모드 전환 | | 화면 전체를 대응 절차로 전환 |
| 3 | 112 신고 안내 확인 | 신고 절차 안내 | 😖 혼란 | **한 번에 하나씩** 제시 |
| 4 | 금융회사 지급정지 안내 확인 | 해당 금융회사 연락처 표시 | | 전화 연결 버튼 직접 제공 |
| 5 | 증거 보존 안내 확인 | 문자·전화 이벤트 보존 | | 자동 보존, 사용자 조작 최소화 |
| 6 | — | **사건 경위 자동 요약 생성** (LLM) | 😌 안도 | 신고 시 그대로 사용 가능한 형태 |
| 7 | 보호자와 대응 항목 분담 | 보호자 웹에 체크리스트 공유 | | 누가 무엇을 할지 명확히 |
| 8 | 조치 완료 기록 | 상태 업데이트 | | |

**이 여정의 특수성**

| 고려사항 | 설계 반영 |
|---|---|
| **사용자는 공황 상태** | 선택지를 최소화. 한 화면에 하나의 행동만 |
| **수치심으로 알리기 어려움** | "보호자에게 알리기"를 강요하지 않되, 권장 |
| **시간이 가장 중요** | 지급정지는 골든타임이 존재. 절차를 가장 앞에 |
| **사용자가 스스로 설명하기 어려움** | LLM이 사건 경위를 대신 요약 |

> **문구 설계 원칙 (1단계)**
> "왜 송금하셨나요" 같은 표현은 절대 사용하지 않습니다. 사용자는 이미 자책하고 있으며, 서비스가 비난하면 즉시 이탈합니다.
> **"지금 바로 해야 할 일이 있습니다"** — 과거가 아니라 다음 행동으로 시선을 옮깁니다.

### 2-4. 보호자 여정 (박지은 — 생활지원사)

**상황**: 다른 어르신 댁으로 이동 중, 담당 어르신의 위험 알림 수신

| 단계 | 사용자 행동 | 시스템 동작 | 소요 목표 |
|---|---|---|---|
| 1 | 알림 수신 (모바일 웹 푸시) | 고위험 사건 발생 시 즉시 발송 | 즉시 |
| 2 | 알림 클릭 → 웹 접속 | **담당자 대시보드** 표시 | ~5초 |
| 3 | **누가 위험한지 확인** | 담당 25명 중 위험 순 정렬 | ~10초 |
| 4 | **상황 파악** | 위험 유형·시각·행동 신호·현재 상태 | **~30초** |
| 5 | **[바로 전화하기]** 클릭 | 통화 연결 | 즉시 |
| 6 | 어르신과 통화 | — | |
| 7 | 대응 체크리스트 확인 | 함께 수행할 항목 표시 | |
| 8 | 사건 상태 갱신 | RESOLVED 기록 + **업무 이력 저장** | |

**알림 내용 요구사항 (4단계가 핵심)**

```
김영희 어르신에게 위험 전화가 감지되었습니다.

유형: 공공기관 사칭 의심
위험 수준: 매우 위험
발생 시각: 14:32
현재 상태: 통화 종료
행동 신호: 앱 설치 요구

[바로 전화하기]  [상황 확인]
```

> **30초 제약**: 박지은은 이동 중입니다. 스크롤해야 파악되는 정보 구조는 실패합니다.
> 위험 유형 / 시각 / 행동 신호 / 현재 상태 **4가지가 첫 화면에** 있어야 합니다.

> **⭐ 1:25 구조가 만드는 추가 요구 (3단계)**
> 자녀 보호자에게는 없던 단계입니다. 동시에 여러 명에게 위험이 발생할 수 있으므로,
> **"지금 누구부터 연락해야 하는가"** 를 판단할 화면이 먼저 필요합니다.
> 이것이 보호자 웹을 단순 알림 확인이 아닌 **관리 대시보드**로 만드는 이유입니다.

### 독거노인 전환 배경 (1주차)

경쟁 서비스 조사 결과, **가족 알림 기능은 이미 존재**했습니다 (피싱아이즈 '가족 돌보미').
반면 **독거노인 대상 실시간 피싱 방지 서비스는 발견되지 않았습니다.** 관련 서비스는 전부 복지관·지자체의 **일회성 집합 교육**이었습니다.

| 근거 | 수치 |
|---|---|
| 65세 이상 1인 가구 비율 | **23.6%** (2025년, 역대 최고) |
| 60대 스마트폰 사용률 | 100% — 기기는 문제가 아님 |
| 70대 이상 디지털정보화 활용 수준 | **20.8%** — 설치·설정이 문제 |
| 독거노인 대상 피싱 방지 서비스 | **없음** (교육 프로그램만 존재) |

**참조 모델**: 응급안전안심서비스(화재·낙상 감지 → 담당자 알림)가 이미 국가 사업으로 작동 중입니다.
돈워리는 **동일 구조를 금융사기 영역으로 확장**합니다.

**변경 내용**
- 김영희: 65세 배우자 동거 → **68세 독거**, 돌봄서비스 연결
- 보호자: 이수빈(자녀) → **박지은(생활지원사)** 로 교체, 이수빈은 보조 페르소나로 유지
- 보호자 웹: 알림 확인 화면 → **1:25 관리 대시보드**
- 신규 요구: 어르신 폰에서 본인인증·설치 부담 제거
