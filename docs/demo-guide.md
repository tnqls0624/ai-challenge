## 2. 심사자가 확인할 핵심

1. 탐지 점수보다 “지금 할 행동”이 먼저 보임
2. 문자와 이후 전화의 관계를 하나의 사건으로 판단
3. CRITICAL에서 사전 동의된 보호자가 개입
4. 생활지원사가 25명 중 우선 대응 대상을 판단
5. 피해가 발생하면 S0~S4 체크리스트로 이어짐
6. 원문 최소수집·UNKNOWN·fallback이 제품 흐름에 포함됨

## 3. 공개 데모 6개

| 순서 | 데모 | fixture | 예상 결과 |
|---:|---|---|---|
| 1 | 정상 택배 | `SCN-001` | SAFE, 오탐 없음 |
| 2 | 건강보험 사칭 | `SCN-024` | CRITICAL, 송금+기관 사칭 |
| 3 | 카드 배송 | `SCN-029` | CRITICAL, 악성 URL+결제 |
| 4 | 검찰 사칭 전화 | `SCN-025` | 문자–전화·설문·자동 알림 |
| 5 | 정상 병원 전화 | `SCN-003` | SAFE, 정상 번호 |
| 6 | 피해 발생 | `SCN-028` | CRITICAL S4, 긴급 대응 |

모든 시나리오는 합성 데이터이며 실제 FCM·외부 API를 호출하지 않습니다.
각 시나리오는 브라우저의 공통 RiskEngine에서 계산하며 단계 전환과 체크리스트는
`sessionStorage`에 최대 24시간만 유지됩니다. 새로고침 복원과 console 오류 없음까지
로컬 production build에서 확인했습니다.

## 5. Android 동시 데모

1. 보호자 웹에서 대상자와 활성화 코드 생성
2. Android에서 코드·연결·동의
3. 공유 메뉴 또는 붙여넣기로 위험 문자 입력
4. 로컬 경고 확인
5. 서버 최종 결과와 보호자 웹 사건 확인
6. 실기기 스파이크를 통과한 경우에만 자동 문자·전화 흐름 시연

자동 감지가 불안정하면 숨기지 않고 직접 입력을 기본 흐름으로 사용하며 제한사항을 설명합니다.

## 7. 심사 질문

### 왜 웹앱만 만들지 않았나요?

보호자·심사 데모는 웹으로 제공하지만 문자 알림과 수신 전화 callback은 Android 시스템 기능이 필요합니다. 따라서 Android+웹 구조입니다.

### 왜 Python이 아니라 NestJS인가요?

P0는 모델 추론보다 인증·사건·상태·외부 API·알림이 중심입니다. 웹과 TypeScript를 공유하고 운영 서비스를 하나로 유지합니다. Python은 데이터 정제·평가에만 사용합니다.

### AI는 무엇을 하나요?

결정적 규칙·평판·신호가 위험 수준을 정하고 LLM은 확정된 근거를 쉬운 문장과 사건 요약으로 바꿉니다. LLM은 수준과 알림 여부를 바꾸지 못합니다.

### 개인정보를 보호자에게 얼마나 보여주나요?

P0는 연결별 MINIMAL/BASIC 공유만 적용하고 문자 원문은 보호자에게 제공하지 않습니다. P1에서만 사건별 15분·1회 EXTENDED 공유를 검토합니다. 통화 음성·전체 연락처·계좌정보는 수집하지 않습니다.

### 데모가 실제 서비스와 같은가요?

판정 구현은 공통 RiskEngine을 사용하지만 공개 안전을 위해 입력·평판·푸시는 합성 fixture이고 운영 DB·FCM에는 접근하지 않습니다.

## 8. 데모 전 확인

- 시크릿·개인정보가 화면과 개발자 도구에 없음
- 브라우저 새 프로필에서도 로그인 없는 데모 가능
- 6개 scenario를 순서·개별 진입 모두 가능
- 모바일·desktop 레이아웃 확인
- 새로고침·뒤로가기·session 만료 확인
- 합성 데이터·모의 알림 label 표시
- 실제 테스트 계정 비밀번호와 APK URL 확인
- 발표용 화면 확대·알림 차단 설정 확인
