# 위험도별 경고·알림 정책

> 관련 문서: [PRD.md](../PRD.md) · [user-research.md](user-research.md) · [기획서.md](기획서.md)
>
> 작성: 1주차 (화면 IA 인터뷰 중 확정)
>
> 이 문서는 화면 IA와 설정 화면 설계의 직접 입력물입니다.

---

## 1. 기본 원칙

**두 사용자는 서로 다른 것을 받습니다.**

| | 김영희 (보호 대상자, 68세 독거) | 박지은 (보호자, 생활지원사) |
|---|---|---|
| 받는 것 | **위험 경고** | **보호자 알림** |
| 기기 | 본인 Android 폰 | 웹 대시보드 + 푸시 |
| 시점 | 문자·전화 수신 즉시 | 고위험 상황에서만 |
| 목적 | "지금 이 행동을 하지 마세요" | "김영희 어르신이 위험합니다" |
| **담당 규모** | 본인 1명 | **20~25명** |

```
문자·전화 수신
   ↓
① 김영희 폰에 경고 표시
   ↓
② 자동 알림(CRITICAL) 또는 김영희가 요청
   ↓
③ 박지은에게 보호자 알림
   ↓
④ 박지은이 김영희에게 전화
```

> **보호자 유형에 따라 정책이 달라집니다**
> 생활지원사는 20~25명을 담당하므로 알림이 겹칠 수 있습니다.
> 자녀는 1명만 담당하므로 그런 문제가 없습니다.
> 이 차이가 4장(보호자 유형별 정책)의 근거입니다.

## 2. 기본값 (권장 설정)

사용자가 설정을 바꾸지 않으면 적용되는 값입니다.

| 위험도 | 김영희 (보호 대상자) | 박지은 (보호자) |
|---|---|---|
| **CRITICAL** | 🔴 **전체화면 강제 경고** | ✉️ **자동 알림** |
| **HIGH** | 🔴 전체화면 경고 | 김영희가 요청 시 |
| **CAUTION** | 🟡 알림창 → 탭하면 경고 화면 | 김영희가 요청 시 |
| **UNKNOWN** | ⚪ 알림창 "확인이 필요합니다" | 김영희가 요청 시 |
| **SAFE** | 표시 없음 | 없음 |

### 전체화면 경계선: HIGH / CAUTION 사이

PRD 9.2의 강제 규칙과 맞물립니다.

```
확정 악성 URL 일치 → 최소 HIGH → 반드시 전체화면 경고
```

악성 URL이 확인된 문자는 예외 없이 전체화면으로 차단됩니다.

### CRITICAL 자동 알림의 근거

사용자가 이미 설득된 상태에서는 스스로 [확인 요청]을 누르지 않습니다.

따라서 CRITICAL에서는 **사용자 동작 없이** 보호자에게 알립니다. 이것이 설득된 상태를 무력화하는 유일한 방법입니다.

> **혼자 사는 사용자에게 더 중요합니다**
> 보이스피싱의 고립 유도 수법("가족에게 말하지 마세요")은 혼자 사는 사용자에게 **필요하지 않습니다.**
> 이미 고립되어 있어, 곁에서 이상함을 눈치챌 사람이 없습니다.
> 자동 알림은 그 부재한 외부 검증을 대신합니다.

> ⚠️ **사전 동의 필수**
> PRD 3.2는 "사용자의 동의 없는 보호자 알림"을 금지합니다.
> 자동 알림은 **보호자 연결 시점에 별도 동의 항목**으로 받아야 합니다.
> → 보호자 연결 화면에 동의 UI 필요 (IA 반영 사항)

### UNKNOWN 처리

PRD 6.2 "단정하지 않기" 원칙에 따라, 데이터가 부족하면 안전/위험 어느 쪽으로도 단정하지 않습니다.

알림창에 "확인이 필요한 문자입니다"로 표시하고, 탭하면 **무엇을 판단할 수 없는지** 설명합니다.
(PRD 6.5 투명한 근거 — "추가 확인이 필요한 사항")

## 3. 사용자 설정

### 3-1. 권한 분리

각자 **자기 영역만** 통제합니다. 보호자가 어르신의 설정을 바꿀 수 없습니다.
(PRD 4.2 비목표 — "타인이 어르신의 스마트폰을 원격 통제하는 서비스" 방지)

| 김영희가 정하는 것 | 박지은이 정하는 것 |
|---|---|
| 내 폰에 경고가 어떻게 뜨는지 | 어느 수준부터 알림을 받을지 |
| 보호자에게 자동으로 알릴지 여부 | 알림 방식 (푸시 / 이메일) |
| 공유 수준 (최소/기본/확장) | 담당 목록 정렬·필터 |

> **설정 접근의 현실적 제약**
> 70대 이상 디지털정보화 활용 수준은 **20.8%** 입니다. 어르신이 설정 화면에 진입할 가능성은 낮습니다.
> 따라서 **기본값이 곧 실제 설정**이라고 보아야 하며, 프리셋 변경은 생활지원사가 방문 시 함께 조정하는 흐름을 상정합니다.
> 단, **변경 권한은 어르신에게 있고** 보호자는 대신 조작할 뿐입니다 (동의 후 진행).

### 3-2. 김영희 설정 — 3개 프리셋

표 형태의 세부 설정 대신 프리셋으로 제공합니다. (고령자 UX: 한 번에 하나의 선택)

| 프리셋 | 전체화면 | 알림창 | 보호자 자동알림 |
|---|---|---|---|
| **꼼꼼하게** | CAUTION부터 | CAUTION부터 | HIGH부터 |
| **보통** ⭐ 기본값 | HIGH부터 | CAUTION부터 | CRITICAL만 |
| **가볍게** | HIGH부터 | **표시 안 함** | CRITICAL만 |

**프리셋 설명 문구 (앱 표시용)**

| 프리셋 | 설명 |
|---|---|
| 꼼꼼하게 | 조금이라도 의심스러우면 알려드려요 |
| 보통 | 위험한 문자만 알려드려요 |
| 가볍게 | 정말 위험할 때만 알려드려요 |

### 3-3. 끌 수 없는 것 (안전장치)

어떤 프리셋에서도 다음은 비활성화할 수 없습니다.

```
CRITICAL → 전체화면 경고 + 보호자 자동알림
```

이유: 이것을 끌 수 있으면 서비스의 존재 이유가 사라집니다.
설득당한 사용자가 범죄자의 지시로 경고를 끄는 상황도 방지합니다.

### 3-4. 박지은 설정 (보호자)

| 항목 | 선택지 | 기본값 |
|---|---|---|
| 알림 받을 기준 | CRITICAL만 / HIGH부터 / 어르신 요청 시에도 | CRITICAL만 |
| 알림 방식 | 웹 푸시 / 이메일 / 둘 다 | 웹 푸시 |
| **알림 묶음 처리** | 개별 / 5분 단위 묶음 | 개별 |

> PRD FR-002의 `alert_threshold`(HIGH 또는 CRITICAL)를 확장한 형태입니다.

## 4. 보호자 유형별 정책 — 1:25 구조의 영향

생활지원사는 **20~25명**을 담당합니다. 자녀(1:1)와 다른 문제가 발생합니다.

| | 자녀 (1:1) | 생활지원사 (1:25) |
|---|---|---|
| CRITICAL 알림 빈도 | 하루 0~1건 | **동시 발생 가능** |
| 필요한 판단 | "지금 전화할까?" | **"누구부터 전화할까?"** |
| 알림 형태 | 단건 알림으로 충분 | **우선순위 목록 필요** |
| 기본 공유 수준 | 최소 (감시 우려 큼) | 기본 (직무상 개입) |

### 4-1. 동시 다발 상황 처리

같은 수법이 지역에 유포되면 담당 어르신 여러 명에게 동시에 위험이 발생할 수 있습니다.

```
14:32  김영희  CRITICAL  기관사칭 + 송금 요구
14:33  박순자  HIGH      악성 URL 문자
14:35  이만수  CRITICAL  기관사칭 + 앱 설치 요구
```

이때 필요한 것은 알림 3건이 아니라 **"누구부터"** 입니다.

**정렬 기준 (대시보드 기본값)**

1. 위험도 (CRITICAL → HIGH → CAUTION)
2. 행동 신호 유무 (송금·앱 설치 요구가 확인된 건 우선)
3. 발생 시각 (최근 순)
4. 미대응 시간 (오래 방치된 건 상향)

### 4-2. 알림 피로 방지

25명 × 하루 여러 건이면 알림이 무의미해집니다. 다음으로 완화합니다.

| 장치 | 내용 |
|---|---|
| **기본 임계값 상향** | 생활지원사 기본값은 CRITICAL만 (자녀와 동일하나 이유가 다름 — 자녀는 사생활, 생활지원사는 물량) |
| **묶음 옵션** | 5분 내 발생 건을 하나로 묶어 전송 (선택) |
| **대응 완료 반영** | 이미 처리한 건은 목록에서 하향 |
| **근무 시간 설정** | 야간에는 CRITICAL만 (P1 검토) |

> ⚠️ **미해결 — 야간·휴무 시간 처리**
> 생활지원사는 근무 시간이 정해져 있습니다. 야간에 CRITICAL이 발생하면 누가 받는가?
> 후보: ① 알림 보관 후 익일 전달 ② 대체 보호자(친지) 지정 ③ 공식기관 안내로 대체
> → 3주차 사용자 테스트에서 실제 생활지원사에게 확인 필요

### 4-3. 보호자가 없는 경우

돌봄서비스에 연결되지 않았고 친지도 없는 사용자가 존재합니다.

이 경우에도 **탐지·경고·대응 안내는 그대로 작동**하며, 보호자 알림만 비활성화됩니다.
대신 CRITICAL 발생 시 **공식기관 확인 경로**를 제시합니다.

```
CRITICAL 발생 → 보호자 없음
   → "지금 이 번호로 확인하세요"
   → 금융감독원 1332 / 경찰청 112 원터치 연결
```

혼자여도 **검증 경로 자체는 제공**한다는 원칙입니다.

## 5. 미해결 사항

화면 문구·설계 단계에서 결정해야 할 항목입니다.

### 5-1. "확인 요청"과 "물어보기"의 구분

CAUTION·UNKNOWN에서도 보호자에게 연락할 수 있게 했는데, HIGH 이상과 성격이 다릅니다.

| | HIGH 이상 | CAUTION · UNKNOWN |
|---|---|---|
| 상황 | 위험이 확인됨 | 애매함 |
| 보호자에게 가는 메시지 | "위험이 감지되었습니다" | "이거 뭔지 봐주세요" |
| 보호자의 반응 | 즉시 전화 | 확인 후 답변 |

같은 버튼·같은 알림으로 처리하면 보호자가 매번 긴급 상황으로 인지합니다. 25명을 담당하는 생활지원사에게는 특히 치명적입니다.
**두 가지를 시각적·문구상 구분**해야 합니다.

### 5-2. 전체화면 경고의 기술적 제약

전체화면 경고는 Android **다른 앱 위에 그리기**(overlay) 권한이 필요합니다.

- 사용자가 설정에서 직접 권한을 켜야 함
- 최신 Android일수록 제약 증가
- 기기 제조사별 편차 존재

→ 권한이 없거나 동작하지 않는 경우의 **대체 경로(알림창)** 를 반드시 준비해야 합니다.
(PRD 20장 예외 상황 처리와 동일한 맥락)

## 6. 결정 이력

| 항목 | 결정 | 근거 |
|---|---|---|
| 경고 방식 | 전체화면 강제 | 개입 확실성 우선. 서비스 컨셉("행동 제동")과 일치 |
| 전체화면 경계 | HIGH부터 | PRD 9.2 강제 규칙과 정합. 오탐 부담 완화 |
| CRITICAL 보호자알림 | 자동 | 고립 수법 무력화. 설득당한 상태에서도 작동 |
| HIGH 보호자알림 | 사용자 요청 | 자기결정권 존중. 설정으로 자동 전환 가능 |
| CAUTION·UNKNOWN | 알림창만 | 오탐 부담 및 보호자 알림 피로 방지 |
| 설정 권한 | 각자 자기 영역 | PRD 4.2 비목표(원격 통제) 회피 |
| 보호자 유형 | 생활지원사 기본 | 독거노인 전환. 기존 돌봄 인프라 활용 |
| 1:25 대응 | 우선순위 정렬 대시보드 | 동시 다발 시 "누구부터"를 판단해야 함 |
| 보호자 부재 시 | 공식기관 연결로 대체 | 혼자여도 검증 경로는 제공 |
| 설정 형태 | 3개 프리셋 | 고령자 UX. 10칸 표 대신 3개 선택지 |
